# Архитектура

Этот документ объясняет, из чего состоит фронтенд рассадки и почему он так устроен.
Практические правила работы с кодом — в README пакетов (`libs/seating/README.md`,
`apps/seating-lab/README.md`); здесь — общая картина.

## Слои

```
┌─────────────────────────────────────────────────────────────────┐
│ apps/seating-lab — стенд: конфигуратор, витрина, сайт-хост,     │
│                      WebView-хост, макет оплаты                  │
├─────────────────────────────────────────────────────────────────┤
│ @tickets/seating/embed — SDK встраивания (iframe + протокол v2) │
├─────────────────────────────────────────────────────────────────┤
│ @tickets/seating — ядро:                                        │
│   модель и валидация · кодеки · два рендерера (PixiJS) ·        │
│   клиенты api.ts / sales-api.ts                                 │
├─────────────────────────────────────────────────────────────────┤
│ Backend TomCell (HTTP, Keycloak JWT)                            │
└─────────────────────────────────────────────────────────────────┘
```

Приложение не содержит собственной логики схемы: любое правило геометрии, любой расчёт
доступности и любая форма денег живут в ядре или приходят с сервера. Стенд — это интерфейс
над ядром; продуктовый фронт будет использовать то же ядро тем же способом.

## Ядро `@tickets/seating`

Разделено по ответственности (все файлы в `src/`):

| Часть | Файлы | Ответственность |
|---|---|---|
| Модель | `model.ts`, `units.ts`, `money.ts` | Типы контракта геометрии и свойств, единицы (тысячные условной единицы = мм при единице «метр»), деньги `SalesMoney` |
| Валидация | `validation.ts` | Повторение серверных правил до запроса: наложение мест, пересечение рядов, пролом нумерации, пустые зоны; общий набор контрольных примеров — `testing/seating-validation-cases.json`, побайтно тот же, что в тестах backend |
| Кодеки | `codec.ts`, `geometry.proto`, `generate-rows.ts`, `generate.ts` | Компактная передача состава (protobuf) и параметрическая генерация рядов |
| Рендеринг | `scene.ts`, `editor.ts`, `geometry-layout.ts`, `seat-textures.ts`, `theme.ts`, `object-pool.ts`, `spatial-index.ts`, `render-model.ts` | Два специализированных рендерера на PixiJS: `scene` — витрина покупателя (чтение, панорамирование, выбор), `editor` — студия разметки (черчение, привязки, правка). Общее математическое ядро и LOD-пороги гарантируют, что кресло в редакторе и на витрине выглядит одинаково |
| Клиенты | `api.ts`, `sales-api.ts`, `duplicate.ts`, `imports.ts` | Типизированные клиенты REST конфигуратора и продаж, перенос схемы с подложкой и размещением, импорт |
| Встраивание | `embed/` | React-обёртка `SeatingWidget`, функция `mountSeatingWidget`, протокол сообщений v2, нативный мост `createNativeBridge` |

## Виджет и протокол встраивания

Виджет — отдельная страница (`widget.html`) и отдельный бандл: встраиваемая часть не тянет
интерфейс стенда. Хост подключает её одним из двух способов:

- **React** — `<SeatingWidget src context onSelectionChange …>` из `@tickets/seating/embed`;
- **любой сайт** — `mountSeatingWidget({ container, src, context })` с методами
  `updateContext` и `destroy`.

Дальше работает версионированный протокол `postMessage` (v2):

- в строку адреса уходят только идентификатор экземпляра и origin родителя; токен и контекст
  передаются сообщением;
- обе стороны проверяют `event.origin`, окно-источник, версию протокола и идентификатор
  экземпляра; чужое сообщение молча отбрасывается;
- контекст (`WidgetContext`) адресует продажи показом: `occurrenceId` + `testMode: true`;
  `configurationId` остался только для предпросмотра конфигурации организатором;
- виджет публикует события `ready`, `selectionChanged`, `resize`, `error`,
  `reservationCreated`, `expired`, `purchaseCompleted`; хост отправляет команды `context`,
  `clearSelection`;
- при обновлении контекста состав перечитывается только при смене адреса API, схемы или
  редакции — продление токена выбор не сбрасывает.

Мобильные приложения встраивают не сам виджет, а страницу `webview-host.html`: она держит
виджет в собственном iframe и перекладывает те же сообщения через нативный мост
(`createNativeBridge`): события уходят в `ReactNativeWebView.postMessage` или
`JavaScriptChannel`, команды приходат вызовом `window.seatingBridge.receive(...)`.
Примеры кода Flutter и React Native — в `apps/seating-lab/README.md`.

## Тестовый сайт (`site-host.html`)

Изображает будущий сайт организатора: подключает виджет через `mountSeatingWidget` с
автоподстройкой высоты, содержит панель параметров встраивания (токен покупателя, показ,
режимы) и журнал событий. Открывается со второго экземпляра стенда на порту 4300, чтобы
встраивание было кросс-доменным, как на настоящем сайте (см.
[`run-and-stand.md`](run-and-stand.md)).

## Редакции и конкурентность

Схема — неизменяемые редакции: каждая запись зоны создаёт новую редакцию конфигурации.
Клиент работает с токенами версий (`versions` в ответах: `zoneVersion` — атрибуты,
`compositionVersion` — состав, `configurationVersion`/`configurationRevision` — конфигурация).
Зона с изменившимися только атрибутами уходит `PATCH` без перезаписи мест; изменившийся состав —
полным `PUT` с перечитыванием (сервер выдаёт UUID новых рядов, мест и столов). Конфликт версий
— `409` с объяснением.

## Безопасность встраивания (текущие границы)

Тестовый режим передаёт токен покупателя сообщением от хоста; короткоживущей сессии
встраивания, allowlist происхождения и CSP пока нет — до их появления `webview-host.html`
нельзя включать в продуктивные сборки мобильных приложений. Ограничения собраны также в
README стенда и в реестре разрывов backend.
