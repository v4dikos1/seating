# seating-lab

Рабочее место конфигуратора залов: три поверхности над одним ядром `@tickets/seating`.

1. **Организатор** — свои залы и схема мест.
2. **Администратор** — то же плюс справочник площадок и помещений.
3. **Витрина** — встраиваемая клиентская часть, которую подключает основной фронт.

Всё взаимодействие идёт через интерфейс: идентификаторы не вводятся руками, площадка и
помещение выбираются списком, зал создаётся формой, схема рисуется на холсте. Возможности,
которых в API ещё нет, помечены словом «скоро» рядом с тем местом, где появятся, и собраны
в разделе «Что появится позже».

```bash
npm run dev      # http://localhost:4200 (из корня репозитория)
```

Второй экземпляр для кросс-доменного встраивания: `npm run dev:site` (порт 4300).

## Вход

Два способа: логин с паролем через Keycloak либо готовый access token. Значения сервера
входа берутся из конфигурации запущенного хоста backend (`src/Web/appsettings.Development.json`
репозитория backend, раздел `Keycloak`): `BaseUrl`, `Realm` и клиенты из `Provisioning.Clients`
(`OrganizerClient`, `AdminClient`, `CustomerClient`). Клиенты публичные, секрет не нужен.

Вход по паролю работает только если адрес страницы разрешён приложению в Keycloak. Клиенты
провижинятся с redirect URI портов 8000/8001/3000, поэтому с `localhost:4200` браузер получит
отказ ещё до ответа — в этом случае используется вход по токену, и форма прямо об этом говорит.

Полномочия сервер проверяет по базе, а не по содержимому токена. Организатору нужны
`SeatingRead` и `SeatingManage`, администратору дополнительно платформенные `VenueRead`
и `VenueManage`. Организации, заведённые до появления полномочий конфигуратора, их не
получают автоматически — маршрут конфигуратора ответит им `403`.

Если токен истёк во время работы, приложение не выбрасывает из сеанса: поверх экрана
открывается окно повторного входа, а несохранённая схема остаётся на месте.

## Конфигуратор

| Инструмент | Что делает |
|---|---|
| Выбор (V) | щелчок — место/стол, рамка — несколько, перетаскивание — сдвиг выбранных |
| Зона (Z) | прямоугольник новой зоны; код, название и цвет подбираются автоматически |
| Ряд (R) | линия, вдоль которой равномерно раскладываются места |
| Место (S) | одиночное место в выбранный ряд |
| Стол (T) | стол с местами по кругу в зоне со столами (режимы Whole, Individual, MinimumQuantity) |

`Delete` удаляет выбранные места, `Esc` снимает выбор, `Ctrl+Z` и `Ctrl+Shift+Z` — отмена и
возврат. Перемещение камеры (`W/A/S/D`, стрелки, `+`/`−`, `[`/`]`) работает, когда холст
в фокусе: иначе `S` одновременно выбирало бы инструмент «Место» и уводило камеру вниз.

Быстрые пространственные действия над выделением (поворот, выравнивание, распределение,
привязка к сетке, выпрямление ряда) живут только на плавающей панели над холстом —
там, где работает мышь. Правая панель — параметрический инспектор: точный угол,
формула нумерации, иерархия свойств. Одинаковых кнопок в двух местах нет.

Инспектор справа правит зону (название, код, цвет, тип, вместимость свободной зоны, этаж),
подпись ряда и нумерацию с шагом и направлением, добавление мест в ряд и удаление рядов, а также
параметры и продажу столов. Отдельные панели задают общие свойства зоны,
ряда, стола, выбранных мест и зала по умолчанию («Свойства зала»): «Наследовать» снимает объявление,
а «Нет» и «Служебное» — заданные значения, перекрывающие верхний уровень. Границы зоны растут за местами сами;
кнопка «Подогнать границы под места» сжимает их обратно.

### Структура зоны: нумерация и проходы

Ряды и места нумерованной зоны строятся по параметрам, а не расставляются по координатам
вручную. Панель «Структура зоны» задаёт:

- **правило подписей отдельно для рядов и мест** — числовое с произвольным шагом (шаг 2
  от нечётного начала даёт нечётные, от чётного — чётные), буквенное `A, B, C…`
  и произвольный список, плюс обратное направление;
- **разрыв нумерации** — перечень пропускаемых подписей. Пропуск не сдвигает места:
  порядок сохраняется, меняется только подпись. Разрыв допустим, но требует явного
  подтверждения, поэтому до отметки кнопка построения выключена;
- **нумерацию от центрального прохода** — слева от прохода чётные номера к краю, справа
  нечётные к краю. Точка деления берётся из первого продольного прохода, иначе из
  середины ряда;
- **проходы** — продольные (между местами ряда) и поперечные (между рядами), сколько
  угодно и любой ширины. Проход — это пустое место в координатах, отдельного объекта
  в контракте геометрии у него нет.

Панель показывает, что получится, до нажатия: число рядов и мест, размеры, первые подписи
рядов и первого ряда. Те же правила применяет перенумерация выбранного ряда — места при
этом не двигаются, меняются только подписи.

### Проверка схемы

Кнопка «Проверка» на панели вида показывает число находок текущего этажа и открывает отчёт
по всей схеме: уровень, код проверки, что найдено и ссылка «Показать», наводящая камеру
на зону. Тот же отчёт открывается при сохранении.

**Критические находки блокируют запись** — окно не предлагает сохранить, пока наложение
зон, дубль адреса, место вне контура или стол без мест не исправлены. **Предупреждения
сохранить можно, подтвердив их явно**: кнопка называется «Подтвердить и сохранить»,
а подтверждение относится к конкретному набору предупреждений — если набор изменился,
отчёт откроется снова.

Валидатор принадлежит ядру, поэтому последнее слово за сервером: кнопка «Сверить
с сервером» в отчёте запрашивает `GET /api/seating-configurations/{id}/validation`
и показывает находки ядра по **сохранённой редакции** — не по текущему черновику
на холсте. Проход редактора нужен, чтобы видеть находки во время правки, не обращаясь
к серверу на каждый ход.

Что именно проверяется и чего в контракте нет — в [README библиотеки](../../libs/seating/README.md).

### Единицы

Единица схемы равна метру помещения, а целые числа контракта — миллиметры
(основание — раздел о калибровке в [`docs/backend/seating-configurator.md`](../../docs/backend/seating-configurator.md)).
Поэтому кресло на холсте имеет ширину 45 см, шаг сетки выбирается из 45–100 см,
координаты и размеры печатаются в метрах, а строка состояния холста показывает
масштаб в пикселях на метр и координаты курсора.

Схема, нарисованная в чужом масштабе (например, с шагом мест в 18 метров), видна сразу:
инспектор зоны показывает измеренный шаг, предупреждает и даёт привести зону к настоящему
шагу одним действием — оно меняет геометрию явно и отменяется через `Ctrl+Z`.

### Подложка этажа

Подложка — план помещения в PDF, по которому обводятся зоны и размечаются ряды. Сервер
по ней ничего не создаёт. Работа с ней собрана в окне «Подложка этажа» из трёх шагов:
файл и страница → две точки и расстояние между ними в метрах → проверка результата,
где видно, сколько зала приходится на пиксель плана и каковы размеры страницы. Если
получилось неправдоподобно (например, план шириной в метр), окно говорит об этом прямо.

На холсте подложка переключается и приглушается кнопками панели вида; эти настройки
сессионные и на сервер не уходят. Если геометрия лежит далеко от плана, холст сообщает
расстояние и предлагает показать любое из двух.

Сохранение отправляет только изменённые зоны со всех этажей схемы, по одной, подставляя версию из предыдущего
ответа. Зона, у которой изменились только атрибуты, уходит методом `PATCH`: сервер добавляет
снимок атрибутов над прежним составом, места не переписываются, и перечитывать зону не нужно.
Зона с изменённым составом уходит полным `PUT` и перечитывается: ключи рядов и мест выдаёт
сервер, а в ответе записи их нет.

## Витрина и встраивание

Клиентская часть — отдельная страница `/widget.html` и отдельный бандл. Хост подключает её
через `@tickets/seating/embed`:

```tsx
import { SeatingWidget } from '@tickets/seating/embed'

<SeatingWidget
  src="https://seating.tomcell.am/widget.html"
  context={{ apiRoot, configurationId, revision, token, locale: 'ru', maxSelection: 10 }}
  onSelectionChange={setSeats}
/>
```

В рабочем фронте эту обёртку использует `customer-portal` на маршруте
`/seating?configurationId=…` (`NEXT_PUBLIC_SEATING_WIDGET_URL` — адрес этой страницы).
Контекст пересылается сообщением при каждом изменении, поэтому хост обязан его запоминать:
новый объект на каждый рендер — это поток сообщений. Продление токена схему не перечитывает
и выбор не сбрасывает, состав перечитывается только при смене адреса API, схемы или редакции.

Для внешних сайтов — `mountSeatingWidget({ container, src, context })` с методами
`updateContext` и `destroy`. В строку адреса уходят только идентификатор экземпляра и origin
родителя; конфигурация и токен передаются сообщением. Обе стороны проверяют `event.origin`,
окно-источник, версию протокола и идентификатор экземпляра.

Протокол v2 (`@tickets/seating/embed`, `seatingProtocolVersion`) адресует продажи показом:
`WidgetContext` с `occurrenceId` + `testMode: true` вместо голой `configurationId` (которая
осталась только для предпросмотра конфигурации организатором до привязки к показу — им и
сегодня пользуется эта витрина). Контракт продаж (шаблоны цен, бронь, заказ, оплата) описан
в [`docs/backend/sales.md`](../../docs/backend/sales.md) и реализован клиентом в
`libs/seating/src/sales-api.ts` (`SalesApi`), через который виджет стенда бронирует и оплачивает места.

## Встраивание на сторонний сайт (тестовый режим)

`site-host.html` изображает сайт организатора, который встраивает виджет продаж через SDK хоста
(`mountSeatingWidget`) с автоподстройкой высоты iframe. Чтобы встраивание было кросс-доменным, как
на настоящем сайте, страницу открывают со второго экземпляра стенда на другом порту:

```bash
npm run dev:site      # из корня репозитория; vite --port 4300 --strictPort
```

Затем `http://localhost:4300/site-host.html?occurrenceId=<показ>`: виджет грузится с
`http://localhost:4200/widget.html`, адрес API — `http://localhost:5057`. Токен покупателя вставляется
в панель «Параметры встраивания» вручную (например, из «Инженерной панели» стенда после входа
покупателем); без токена виджет показывает схему и доступность, но не бронирует. Журнал внизу
страницы показывает события, которые получает сайт: бронь, истечение, покупку.

## Встраивание в мобильное приложение (тестовый режим)

> **Только тестовый режим.** Токен покупателя передаётся сообщением от нативного приложения,
> короткоживущей сессии встраивания, allowlist происхождения и CSP ещё нет (спецификация продаж
> §0, §5; артефакт 20 §6.1). Эту страницу нельзя включать в продакшен-сборку мобильного
> приложения — только для разработки и проверки интеграции.

Для Flutter и React Native хост — не сам виджет, а отдельная статическая страница
`/webview-host.html`: она держит `widget.html` в собственном iframe через тот же
`mountSeatingWidget`, что и веб-хосты, и пробрасывает события/команды нативной стороне через
`createNativeBridge` из `@tickets/seating/embed` (`libs/seating/src/embed/native-bridge.ts`).

Схема обмена та же, что у `postMessage` между окнами, только конверт идёт через нативный мост:

1. Страница публикует каждое событие виджета (`ready`, `selectionChanged`, `resize`, `error`,
   а на следующем этапе — `reservationCreated`, `expired`, `purchaseCompleted`) в
   `window.ReactNativeWebView.postMessage(json)` (React Native) и в `window.<channel>.postMessage(json)`
   (Flutter `JavaScriptChannel`, имя канала — параметр `createNativeBridge`, по умолчанию
   `SeatingBridge`). Самое первое такое сообщение (`ready`) содержит `instanceId` — нативная
   сторона должна его запомнить и подставлять в каждую свою команду.
2. Нативная сторона отправляет команды (`context`, `clearSelection`) вызовом
   `window.seatingBridge.receive(JSON.stringify(command))` через `runJavaScript`/`injectJavaScript`.
   `native-bridge.ts` разбирает их строго теми же `parseHostMessage`/`parseWidgetMessage`, что и
   обычный `postMessage`: чужой `instanceId` или version — сообщение молча отбрасывается.

### Flutter (`webview_flutter`)

```dart
import 'dart:convert';
import 'package:webview_flutter/webview_flutter.dart';

String? _instanceId;

final controller = WebViewController()
  ..setJavaScriptMode(JavaScriptMode.unrestricted)
  ..addJavaScriptChannel(
    'SeatingBridge', // то же имя, что channel в createNativeBridge (по умолчанию)
    onMessageReceived: (message) {
      final event = jsonDecode(message.message) as Map<String, dynamic>;
      if (event['type'] == 'ready') {
        _instanceId = event['instanceId'] as String;
        _sendContext(controller, occurrenceId: occurrenceId, buyerToken: buyerToken);
      }
      // selectionChanged / resize / error / reservationCreated / expired / purchaseCompleted —
      // тот же event['type'], тело — по protocol.ts.
    },
  )
  ..loadRequest(Uri.parse('https://seating.tomcell.am/webview-host.html'));

void _sendContext(WebViewController controller, {required String occurrenceId, required String buyerToken}) {
  final command = jsonEncode({
    'protocolVersion': 2,
    'instanceId': _instanceId,
    'requestId': const Uuid().v4(),
    'type': 'context',
    'context': {
      'apiRoot': 'https://api.tomcell.am',
      'occurrenceId': occurrenceId,
      'token': buyerToken, // тестовый режим: токен идёт сообщением, а не строкой адреса
      'testMode': true,
      'locale': 'ru',
    },
  });
  // jsonEncode(command) — JSON-текст; второй jsonEncode превращает его в корректный
  // экранированный строковый литерал JS для runJavaScript.
  controller.runJavaScript('window.seatingBridge.receive(${jsonEncode(command)});');
}
```

### React Native (`react-native-webview`)

```tsx
import { useRef } from 'react';
import WebView from 'react-native-webview';

function SeatingScreen({ occurrenceId, apiRoot, buyerToken }: Props) {
  const webref = useRef<WebView>(null);
  const instanceId = useRef<string | null>(null);

  function sendContext() {
    if (!instanceId.current) return;
    const command = {
      protocolVersion: 2,
      instanceId: instanceId.current,
      requestId: crypto.randomUUID(),
      type: 'context',
      context: {
        apiRoot, occurrenceId,
        token: buyerToken, // тестовый режим: токен идёт сообщением, а не строкой адреса
        testMode: true,
        locale: 'ru',
      },
    };
    // JSON.stringify дважды: внутренний — тело команды, внешний — экранированный
    // строковый литерал для инъекции в JS.
    webref.current?.injectJavaScript(
      `window.seatingBridge.receive(${JSON.stringify(JSON.stringify(command))}); true;`,
    );
  }

  return (
    <WebView
      ref={webref}
      source={{ uri: 'https://seating.tomcell.am/webview-host.html' }}
      onMessage={(event) => {
        const message = JSON.parse(event.nativeEvent.data);
        if (message.type === 'ready') {
          instanceId.current = message.instanceId;
          sendContext();
        }
        // if (message.type === 'purchaseCompleted') { /* перейти на экран билетов */ }
      }}
    />
  );
}
```

## Инженерная панель

Обмен с API и замеры формата геометрии убраны из продуктовых экранов и живут в отдельной
панели (ссылка внизу бокового меню): журнал запросов с кодами и таймингами, а также размер
и время кодека на синтетических схемах 8 000 и 54 000 мест.

## Реестр залов (XLSX)

Раздел администратора «Реестр залов (XLSX)» загружает файл через `/api/files/upload-requests`
и показывает разбор сервера: `GET /api/admin/seating-imports/registry/{fileId}/preview`.
Экран показывает кандидатов сопоставления с площадками и помещениями как подсказки: оператор
должен проверить их вручную. Для распознанного файла без ошибок разбора можно сохранить снимок
отчёта в состояние `PendingReview`. Это не меняет справочник площадок и не публикует данные;
кнопок применения и публикации нет.
Для предпросмотра нужно платформенное полномочие `SeatingManage`; для сопоставления с каталогом
также нужно `VenueRead`. Число мест из реестра — справочная величина источника, а не продаваемая квота.

## Ограничения, видимые в работе

- Состав схемы читается по одной зоне: манифеста и частей сервер не отдаёт.
- Виджет тестового режима показывает цену и доступность, бронирует места и запускает тестовую
  оплату. Выданные билеты покупатель видит в разделе «Мои билеты» после обновления списка.
- Для показов любого размера виджет опрашивает доступность по продаваемым зонам: сервер требует
  `zoneId`, если количество единиц превышает порог `Sales:AvailabilityZoneThreshold`.
- Позальная оптимистическая блокировка (`expectedZoneVersion`): параллельные правки разных зон не конфликтуют, конфликт версий возникает только при одновременной правке одной и той же зоны.
